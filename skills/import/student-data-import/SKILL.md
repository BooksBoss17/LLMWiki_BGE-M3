# Student Data Import

This Role A skill imports student data into `StudentDataSQL/` through the approved root scripts. It owns ingestion workflow and privacy gates, not schema design, router maintenance, or downstream analysis.

## Boundaries

1. Use this skill to preprocess and import rosters, exam item scores, and answer-card manifests.
2. Route analysis, weak-point reports, and safe student/class reports to `skills/analyze/student-data-analysis/SKILL.md`.
3. Route schema, migration, router, script implementation, privacy-governance, or framework changes to `skills/maintain/kb-framework-admin/SKILL.md`.
4. Use only parameterized root scripts under `StudentDataSQL/scripts/`; do not run free-form SQL against raw tables.

## Privacy Gates

1. Keep real student data only under `StudentDataSQL/` runtime areas. Never copy it into `raw/`, `LLMWiki/`, `BGE-M3/`, `skills/`, Git, or vector indexes.
2. Normalized roster/import CSVs, logs, and final messages must not preserve full names, school numbers, exam numbers, student-status numbers, guardian contacts, or raw teacher comments. Ranking snapshots, original answer-card filename mappings, and individual answer records may be kept as local StudentDataSQL analysis evidence when needed, but they must not enter `raw/`, `LLMWiki/`, `BGE-M3/`, `skills/`, Git, safe views, or public/classroom-facing outputs.
3. A roster import requires all fields: `student_id`, `family_name`, `class_id`, `seat_no`, `term_id`, and `gender`. `gender=U` is allowed, but blank/undetermined required fields are not. Stop and ask the user if the source file cannot provide or derive any required field.
4. Score sheets may contain real names only transiently for row matching, answer-card matching, and surname derivation. Do not write real names to normalized CSVs or reports.
5. `--real-data` DB imports require `STUDENT_DATA_DB_KEY` in the current command environment. The teacher owns the key; agents may use a key supplied in the active session, but must not write it into files, logs, Git, reports, vector indexes, or long-term memory. If the key is unavailable, stop after normalized-file generation and validation; do not fall back to dev DB, do not invent a key, and do not import real student data into an unencrypted/dev database.
6. If the user says to import only existing answer cards, include only `present` artifacts in the manifest import.

## Workflow

1. Confirm scope: roster, exam score sheet, item scores, answer-card manifest, or a combined import. Identify `term_id`, `class_id`, `class_name`, `exam/assessment_id`, and source paths.
2. Generate normalized files:
   - Roster: `StudentDataSQL/scripts/preprocess_roster_xlsx.py`
   - School exam score sheet: `StudentDataSQL/scripts/preprocess_school_exam_xls.py`
   - Answer-card manifest: generated by the score-sheet preprocessor when `--copy-answer-cards` is used.
3. Before school exam score-sheet normalization, ensure the canonical roster CSV exists under `StudentDataSQL/runtime/imports/normalized/<class_id>_<term_id>_roster.csv` or pass `--roster-csv`. Score rows must align by `class_id + seat_no` to the roster and copy the roster's `student_id`; do not generate new IDs from score-sheet fields.
4. For school exam score sheets, preserve ranking and score-level fields in the normalized score CSV: `class_rank` from `班级排名`, `grade_rank` from `年级排名`/段排, and `score_band` from `档次`. If the source score sheet lacks these fields, stop and ask the teacher instead of silently dropping them.
5. Enrich item-score files from `StudentDataSQL/runtime/exam-reports/` when the exam has a paper report. Each question should carry `Q*_kp_id`, `Q*_kp_title`, `Q*_key_point`, and `Q*_difficulty_point` when available. `Q*_wiki_path` is optional and should be a teaching wiki path, not the exam report path.
6. Validate normalized files before DB import:
   - Required roster fields are present and nonblank.
   - `student_id` is used externally; legacy `student_code` is internal compatibility only.
   - Score rows match the intended class and assessment, include only students with valid numeric total scores, all `student_id` values exist in the roster import, and school exam rows include `class_rank`, `grade_rank`, and `score_band`.
   - Item columns have max score and question id fields.
   - Manifest rows contain the answer-card artifacts requested by the user; present-only imports must include only `present` artifacts.
   - No forbidden identity fields leak into safe/public outputs.
7. Import in order:
   1. roster with `import_roster.py`
   2. exam item scores with `import_exam_csv.py`
   3. answer-card manifest with `import_answer_card_manifest.py`
8. Verify import JSON, row counts, warnings, and audit output. Report only de-identified counts and file paths.

For concrete command patterns and recovery checks, read `references/exam-score-import-workflow.md` when importing exam scores or answer-card manifests.

## Encrypted Real-Data Staging Rule

For real student data, `STUDENT_DATA_DB_KEY` must be available before preprocessing or importing. If the key is missing, refuse the real-data import before creating persistent CSV/JSON/PNG staging files. Normalized CSV/JSON files and redacted answer-card images are temporary staging only: after roster, exam, and answer-card manifest imports succeed, run `StudentDataSQL/scripts/import_file_artifacts.py --real-data --root StudentDataSQL/runtime/imports --delete-after --json` so file bodies enter the SQLCipher database and unencrypted staging copies are removed. Use `StudentDataSQL/runtime/db/student_data.sqlite3` as the canonical real database; class- or exam-specific encrypted databases are historical snapshots only.
